The heart of it — the atomic transaction

Placing an order is one all-or-nothing transaction. The WHERE stock_quantity >= :qty check plus rows-affected is the concurrency guard — it serializes at the row and makes overselling impossible, however many people order at once.

BEGIN
  INSERT INTO orders (...) RETURNING order_id
  for each item:
    INSERT INTO order_items (order_id, menu_id, quantity, unit_price, line_total)
    UPDATE inventory SET stock_quantity = stock_quantity - :qty
      WHERE branch_id = :b AND menu_id = :m AND stock_quantity >= :qty
    if rows_affected == 0:  ROLLBACK   -- sold out; reject the whole order
  write subtotal, vat_amount (12%), total_price onto the order
COMMIT

Restock uses the same discipline: stock_quantity = stock_quantity + :amount (relative add, never an absolute set — that would clobber a concurrent order's decrement). Partner assignment reuses the identical primitive: UPDATE orders SET partner_id=:me WHERE partner_id IS NULL.

Key decisions

Why this showcases Databricks

  • One platform, two workloads — OLTP (Lakebase) + OLAP (Delta), no external DB, no ETL out.
  • Lakebase = real Postgres — genuine transactions, not an analytics dashboard in disguise.
  • Concurrency is the demo — atomic write proves correctness under load, live.
  • Governed by Unity Catalog — one permission model across app and analytics.

Deliberate scope calls

  • Auth: customer login/signup (PBKDF2-hashed); staff & partner accounts org-provisioned, branch-scoped. Data scoped by role. Production consumer tier lives outside Databricks.
  • Delivery: status stages + mode, not a maps integration.
  • Branches: multiple per city; nearest-branch geo is a stretch.
  • One backend, two frontends — Streamlit (direct) + React (via thin API) share one spine.
